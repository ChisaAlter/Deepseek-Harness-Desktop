# 维护操作

[系统总览](../../../docs/maintenance/README.md)定义何时介入和证据边界。只读取本次相关的功能卡、手册和决定，不遍历全部历史记录。

## 决定是否写记录

- 架构、兼容性、持久格式、发布或测试责任发生长期变化，且后续维护者需要理解取舍：更新 owning 决定；没有对应记录才新建。
- 普通缺陷修复、机械调整和现有契约下的实现变化：在提交 / PR 中说明原因和验证，不强制新建决定。
- 仅当前事实变化：更新它的权威位置，别同时复制到卡、手册、规则和决定。
- 同一决定优先原地更新。真正反转旧决定时新建并互链；历史失败不改写为成功。

## 实施和交付

1. 已获授权的工作直接实施。只有实质方案未定且需要审阅时使用 proposed；可直接写 implemented，不强制经过提案状态。
2. 新内部记录默认单语 `slug.md`，可用中文或英文。已有配对继续同步；双语操作见[配对规则](../../../docs/i18n/README.md)。
3. 必须节按[决策说明](../../../docs/decisions/README.md)组织；只写实际考虑过的备选，不设数量下限，不为填表编造选项。
4. 功能卡只更新当前契约、最近相关验证和证据入口。Allowed touch 是定位提示；在用户授权内扩展必要文件直接同步卡片，不重复索取许可。
5. Bug 先保留可失败的行为复现，再验证修复和 CI 发现范围。真实环境无法自动化时如实标注，不能把静态检查或工具 Pass 当产品验收。
6. [系统性事故](../../../docs/postmortem/README.md)按需复盘，复用已有 issue / QA 证据，不为每个 bug 建复盘或决定。
7. 归档已实施记录用 `node scripts/archive-decision.mjs <record> [--superseded-by <new>]`；失败应保留原文件，封存历史不重写，被否方案保留 verdict。

## 完成检查

[语义自检](references/quality-gate.md)是写作提示，不是追加审批或固定格式汇报。相关脚本与文档门禁通过后，报告实际变化、验证范围和剩余限制即可；不重复整套检查。

用户当前明确要求优先于本文件。不得编造用户偏好、备选方案、测试结果或放行签字。
