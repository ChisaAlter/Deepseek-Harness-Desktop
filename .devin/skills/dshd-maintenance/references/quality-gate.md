# 语义自检（写完决策记录后过一遍）

脚本管结构，这张清单管意思。全部是语义判断，永不进 verify 脚本。写完自检，只向用户报**缺口和写得好的地方**（≤5 行），缺口给具体修法。

## Problem

- [ ] 动机脱离方案也能独立成立——删掉 Decision 再读，还是同一个问题吗
- [ ] 触发清楚：什么破了、什么要变、不做会怎样

## Decision / Proposal

- [ ] 具体到能行动（「为会话存储用 SQLite」，不是「用更好的数据库」）
- [ ] 理由是被 vs 逼出来的：写「决定用 X」就补「X vs Y 为何选 X」

## Alternatives considered

- [ ] ≥2 个真备选；不编没权衡过的选项；「不做/复用」仅当真考虑过才写
- [ ] 每个被否项先写它最强的论据再否——只写弱处是稻草人
- [ ] 否决理由落到具体驱动条件，不是「经验上不行」

## Consequences

- [ ] 代价和收益都写；自问「什么变难了？维护成本是什么？」
- [ ] 收窄/简化注明已知上限与重访触发条件
- [ ] 没有基线不写相对量词——「更快了」说不清基线就降级为事实陈述

## 双语

- [ ] 两侧骨架一致（结构签名绿）；en 侧链接指向 `.en.md` 副本（若有）
- [ ] sidecar 已重录（`--write`），或如实登记 pending

## 汇报形态

```markdown
**语义自检：<filename>**
✅ 稳定：动机独立成立 / 有 2 个真备选 / 后果代价收益兼备
⚠️ 缺口：
- Alternatives — 「做了 vs 不做」稻草人，补一个平行真实选项
建议：修以上 1 处后落盘 / 可接受缺口，直接放行
```

## 生效判据

- 问用户的问题里不再出现翻树/rg 就能答的事实性问题
- 每条缺口带具体修法
- `rejected/` 里被否的路线不再被新会话重提
