# 发布操作流程

本文件是发布执行的唯一当前规则；[用例库](../../qa/production-acceptance-test-cases.md)提供操作步骤，[构建手册](build-release.md)提供装配细节。历史报告只证明其中明确绑定的候选，不约束新流程。自动策略位于 `scripts/release-plan.mjs`，晋级校验位于 `scripts/check-release-acceptance.mjs`。

## 1. 固定范围与完成条件

发布负责人先固定版本、目标平台、要交付的修改和已知缺陷。每个新增问题先判断严重度和影响范围，再决定是否更换候选；不在候选验收中顺带做全面重构或增加功能。用户追加的功能进入下一版，除非用户明确要求本版交付；发生这种范围变更时重新排定候选，并说明哪些验收受影响。

状态按 `preparing → candidate → testing → approved → published` 推进；失败可转 `blocked`，被替换的候选转 `superseded`。每个候选只有一份当前记录：`docs/qa/releases/v<version>/<run-id>.json`。人工执行时更新其中的结果、环境、缺陷和下一步；旧日志保留为证据附件，不再扩写多份“当前状态”。记录的 `state` 只能在真实完成阶段后更新。签字人必须是实际负责放行的人，Agent 不得替用户签名、编造授权或把沉默当批准。

完成条件：精确候选所需 CI 成功；原始安装包资产一致；核心用例全部通过；影响用例已执行或有合法的不适用/风险接受；无未解决的严重产品缺陷；放行签字完整。时间预算不代替这些条件。

## 2. 开发与 CI

局部修复先运行与实际风险相关的测试和可观察的真实验证。没有新改动、新失败或明确未覆盖的风险，不重复已有验证。源码变更的完整 Windows、macOS、GUI、核心和无密钥回归继续在 `test.yml` 执行；纯文档/验收记录及其翻译配对记录提交仅运行快速检查。共享治理与远程组件 lock dry-run 在前，生成目录/第三方声明检查在 vendor 安装后、编译和长测试前。PR 新提交取消同一 PR 的旧测试；main 按 SHA 保留测试，避免补文档取消正在准备的候选资格。候选和晋级关闭运行中取消，并用 `queue: max` 保留等待队列（GitHub 上限 100）；不要重复派发同一个候选。[GitHub 并发规则](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)。

Windows 发版要求同 SHA 最新 main push 的 `Fast checks`、`Desktop unit tests (windows-latest)`、`vendor-gui` 成功。macOS job 保留，失败必须修复和跟踪，但仅在同时发布 DMG 时阻止该候选晋级；共享失败始终阻断。不能挑旧绿色运行或旧 attempt 覆盖最新失败。main 出现失败时先分类、修复或回退相关提交，再把它选作候选。

仅文档或验收记录变更不要求重新生成安装包。验收报告可晚于候选提交；安装包源码 SHA 仍固定不变。修改打包输入才创建新候选，不为补证据或更正报告重建。正式候选稳定后集中执行完整发布门禁，诊断期只复现和验证具体阻塞。

## 3. 生成候选与影响计划

确认目标 main SHA 的相关 CI 已结束，然后手动运行 `release.yml`，显式输入 `candidate_sha` 完整 SHA。它必须在 main 历史上，所有打包 job 固定检出该 SHA；main 随后前进或补文档不改变它。工作流自身的 head SHA 与候选源码 SHA 分开记录。它先检查 CI 资格，再以最近 GitHub 正式版为基线比较全部路径（重命名按删除和新增处理），生成 `Whale-Isle-release-plan` artifact。基线不可手选成“刚才那个提交”来缩小验收。纯文档提交没有完整源码 CI，因此沿用其之前已测的源码 SHA，不为文档另建候选。

- 固定核心集共 26 项：安装与身份、单实例、旧版覆盖升级及数据保留、模型保存与选择、五轮真实对话、停止生成、会话重启恢复、审批允许/拒绝、兄弟工作区、Files 搜索/保存、终端与选区、Git 提交、托盘关闭/退出、默认网络边界与配置持久化。具体 ID 由 `CORE_CASES` 单点定义。
- 影响集按安装/更新、窗口、会话、工作区、远程、插件、外观选择用例库中的相关场景；所有选中用例均需要结果，人工审阅完整 diff 后可增加场景，不能删除自动选择的场景。库外新风险用 `EXTRA-<大写名称>` ID，必须填写可复现的 `procedure` 和真实结果，不为补充验收说明重新打包。
- Electron/Node、实际依赖锁、上游 pin、核心运行时或未能分类的源码修改触发完整用例库。根 package/lock 先做内容比较：仅版本号或测试/发布命令变化不扩大产品范围，依赖、启动/构建命令等变化仍保守全量；分类写入计划供审阅。完整库可按真实前置条件标 N/A，缺工具、缺设备、网络故障属于 Blocked，不属于 N/A。
- 仅发布工具或文档变化不额外增加产品场景，仍须核心集；不会自动把旧包 Pass 写入新包。
- 发布 macOS 时还需要该 DMG 的摘要和 `MAC-INSTALL` 实机记录，覆盖挂载安装、启动、基本会话、退出及升级保留；构建成功不能替代。

Windows 打包后的 unpacked smoke 只执行一次。失败保留原始结果并停止；先判定产品、工具或环境原因，修正具体前置条件后才允许新 attempt。两次同样失败不是自动判断“产品坏了”的依据，第二次通过也不能抹掉首启缺陷。

## 4. 下载与开始验收

候选 artifact 保留 30 天。一次下载后按 run ID/asset ID 缓存复用；不要因为 UI 失败再次下载相同字节。Windows 可显式设置 `GH_PATH` 为已安装 GitHub CLI 的绝对路径。断线只续传 ZIP，下载器最多三次有界尝试，验证 GitHub artifact SHA256 后才将 `.part` 改为 `.zip`，不打印签名地址或 token。

```powershell
$env:GH_PATH = 'C:\Program Files\GitHub CLI\gh.exe'
node scripts/release-download.mjs ChisaAlter/Deepseek-Harness-Desktop <run-id> Whale-Isle-windows-x64 .tmp/release/<run-id>
& $env:GH_PATH run download <run-id> --name Whale-Isle-release-plan --dir .tmp/release/<run-id>/plan
# 将输出的已核验 ZIP 解压到同一候选的 assets 目录，然后核对资产。
node scripts/check-release-assets.mjs .tmp/release/<run-id>/assets v0.3.3 0.3.3 <setup-sha256>
node scripts/check-release-acceptance.mjs init .tmp/release/<run-id>/plan/release-plan.json docs/qa/releases/v0.3.3/<run-id>.json .tmp/release/<run-id>/assets
```

先创建报告父目录。DMG 同样下载原始 artifact，`init` 的最后一个可选参数传 DMG 目录。以上尖括号均为本轮真实值，不是可直接复制的占位证据。旧候选缺 plan/校验器时不能伪造补签：本流程首轮需要包含新发布工具的新候选。没有已发布版本的首次发布需单独定义 bootstrap，当前流程遇到缺基线直接拒绝。

## 5. 固定真实验收环境

安装前记录 Windows/macOS 版本、唯一目标安装目录、profile、升级来源和配置/会话保留基线；停止源码实例。真实安装身份只需在安装后绑定一次（Setup 摘要、已安装 EXE 路径/版本、进程/profile 证据）；后续只有重装、换路径、换包或进程身份不明才重新核验，普通页面操作无需重复解包或给整棵树算摘要。

切换用户资料前，先准备可用的真实网关、模型与密钥、旧版会话基线，以及对应场景所需的 Git、SSH、设备和更新源。外部依赖须从普通安装进程的环境核对：Codex 终端能找到 Git，不证明桌面快捷方式启动的应用也能找到。缺少前置条件时明确标记对应场景 Blocked，继续独立场景，不为此换包、重复下载或编造旧版会话保留结果。仅向验收进程提供已有 Git 等依赖时，记录版本和环境差异，不修改系统环境变量，不将该结果宣传为无需依赖。

Windows PowerShell 5 读取含中文路径的诊断脚本时，使用 UTF-8 BOM 或明确兼容的编码，并先验证解析后的目标边界。工具解析、坐标、选择器或弹出层错误保留为工具证据，不计为产品失败；修正后只补该未完成场景。

从带 MSIX 包身份的工具宿主检查 Windows 默认 profile 时，文件系统虚拟化可能让相同逻辑路径指向宿主的副本。读到旧 peer、缺文件或不同目录链接时，先用没有包身份的原生观察器绑定真实目录与产品 PID；备份、替换、恢复也在该真实目录执行。不能把宿主的副本当作安装版的数据，也不能把两者的差异直接记成产品故障。

正常默认路径安装和旧版本覆盖升级都必须用原始 CI 安装器。优先使用专门的交互式 Windows 测试用户，其 profile 仍是安装版正常默认 profile，不用冒烟 `--user-data-dir` 代替。没有独立测试用户时，可以正常退出全部产品实例后，在同一 Roaming 父目录保留完整原 profile，并让受控副本占用原来的正常默认路径。副本复制不跟随目录链接；先核对容量与链接目标，不让夹具修改原数据或外部用户数据。记录进入、恢复动作；结束后正常退出夹具、恢复完整原 profile，再启动新候选。不能直接用旧稳定版降级用户原数据。

新装验证记录安装器默认目录；覆盖升级沿用旧版选定的目录。涉及用户实际机器时先准备原始新旧安装器和恢复材料，明确每个阶段唯一运行的安装目录，结束时恢复用户原安装位置，避免静默安装意外留下第二个在用的应用。恢复副本和失败现场只在已验证恢复后清理，不为验收要求删除用户原目录。

Shell/任务栏实验额外记录 Explorer 会话起点和旧快捷方式状态；切换干净/升级/污染状态必须从相应已知快照或新登录会话开始。只重启应用不等于重置 Shell。不得把删除夹具后的同一 Explorer 会话当作干净环境，不以窗口属性正确代替用户看到的图标，不将本机现象推广成所有 Windows 的永久保证。窗口变更按 window-motion 卡保留真实合成四角及可见动画验证。

更新正向/失败用例使用可控更新源或隔离升级环境构造更高版本响应，并记录实际服务地址类别与观察结果；不修改公开 latest 来迁就测试。场景的产品前提确实不存在时才可 N/A；更高候选号本身不是放弃更新链验证的理由。

## 6. 失败处理和停止规则

| 分类 | 意义 | 下一步 |
| --- | --- | --- |
| product | 实际用户路径违反产品契约 | 最小真实复现，按严重度修复或记录限制 |
| tool | 选择器、断言、探针或脚本观察错误 | 修观察器，局部验证同一场景，不为此换产品包 |
| environment | 权限、网络、待机、设备或系统状态不具备 | 恢复具体前置条件，在同一包重测该场景 |
| unknown | 尚不能区分以上类别 | 保持阻塞；设计能区分假设的下一次观察 |

产品故障按用户影响分级：Blocker/Critical 包括无法安装/启动、数据或权限边界损坏、主要模型/工具/文件/终端路径不可用、退出失控，未解决禁止发布。Major 是有明确绕过的次要功能故障，需责任人显式接受风险、跟进项和到期日。Minor 是不影响操作的视觉/文案瑕疵，记录责任人、跟进和发布说明，不触发全套重建。用例原 P0/P1/P2 是历史覆盖优先级，不能直接当缺陷严重度。

每次重试必须写明新信息：改了什么前置条件、要区分什么解释、如何判断。相同失败再次出现时停止原样重复完整流程，先核对假设。建议一个诊断假设用 30–60 分钟形成可复现结论或明确阻塞；这不是到点放行。未完成事项必须有具体下一步和责任人，不以“再跑一遍放心”延长工作。

核心 26 项及 MAC-INSTALL 不允许 N/A 或豁免；工具/环境阻塞也不冒充 Pass。非核心受影响项可 N/A（说明真实不适用依据）或保留 Fail/Blocked 并按规则接受风险。未知失败、严重产品缺陷不接受豁免。工具/环境问题标 Blocked，不能直接写成产品 Fail。风险接受示例字段如下，不代表任何真实批准：

本地资产校验测试若不能创建文件符号链接，显式显示环境 SKIP，不能计作通过；GitHub CI 中该权限缺失直接失败，三条真实链接拒绝断言必须执行。不要反复重跑本地全量来等待权限自行变化。

```json
{
  "id": "ISSUE-ID", "kind": "environment", "severity": "major", "status": "open",
  "summary": "具体未验证边界", "evidence": "脱敏证据链接", "owner": "实际负责人",
  "followUp": "跟进任务链接",
  "waiver": { "approvedBy": "实际批准人", "reason": "影响与接受理由", "expiresOn": "YYYY-MM-DD" }
}
```

## 7. 放行和发布

测试者逐项填写报告，release owner 核对 diff/影响范围、已知限制和真实证据，填写 `scopeReview`、`signoff.approvedBy`、带时区的 `signoff.approvedAt`，最后将 `state` 改为 `approved`。机器不能验证一张截图是否真的证明结果，也不能验证姓名代表真实授权；这两项由审阅者负责，禁止自动填充通过或批准。

把脱敏报告及必要证据提交到 main，记住该完整提交 SHA。报告不含凭据、用户会话内容或私人绝对路径；环境路径可以用明确的环境变量表示。公开发行会附带该 JSON，公开前必须检查证据链接可访问且内容可公开。

手动运行 `publish.yml`，输入候选 run ID、版本 tag、Setup SHA256 和 `acceptance_commit`。工作流读取该不可变提交中的固定路径报告，核对它已在 main、计划来自原候选、最新相关 CI、全部选中场景、缺陷与风险接受、原始 Setup/DMG 摘要。通过后直接发布原始字节，并附计划、报告、已知限制和校验和；不重新编译，不把报告提交 SHA 写成候选源码 SHA。

晋级全局串行，上传前再检查版本高于当前 latest，防止较旧候选在较新版之后覆盖更新入口。发布后只核对 Release tag 目标、原始资产摘要和 latest 元数据，记录实际 Release URL；不要重新生成安装包。确有线上缺陷时由负责人明确处理撤回/回退入口并开启新的修复候选，保留失败版本身份，不能移动既有 tag。

## 8. 与已有记录的关系

现有 0.3.3 历史候选、任务栏诊断、手工恢复和未完成签字全部保留，不因流程更新自动变为通过。新机制上线本身不等于已运行 CI 或已发布。旧卡片、旧报告中的“每次全表”“所有平台一律挡 Windows”“两次失败才算产品故障”等发布执行约定由本文件替代；功能不变量和已记录的失败事实继续有效。
