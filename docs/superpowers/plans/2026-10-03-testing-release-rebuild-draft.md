# 测试与发布系统重构草稿

记录日期：2026-10-03

状态：2026-10-03 用户已授权直接重做，并明确废止旧本地与仓库约束。下文保留讨论依据，实施状态见文末；现行流程由 docs/maintenance/README.md 与实际工作流定义。

## 目标与问题

用户要求恢复可持续的开发和交付：完成需求、修复真实用户故障、及时发布更新。现有流程增加了大量测试、维护手续和候选验收工作，但没有证明获得相应的质量收益，还延误了修复交付。不能再以测试数量、文档完整或 CI 次数代替产品结果。

处理方向是整体替换旧发布体系，而不是继续优化其审批与验收手续；不以重构产品底座、建设验证平台或引入新代理框架作为恢复发布的前提。

## 用户已明确确认

- 接受 CI 承载开发阶段的自动测试，不接受在最终发布时反复发现本可提前发现的问题并远程试错。
- 新功能和修复使用工作分支，通过 PR 合入 main，不由 AI 直接提交正式分支。一个需求通常对应一个分支和一个 PR，过程中的多次修改继续留在同一分支。
- 分支中完成实现和相关验证，提出 PR，由用户确认合入；后续交付应由自动化完成，不重新启动一轮人工发布工程。
- AI 不得自行降低需求、弱化断言、用占位行为冒充完成，或为了“放心”追加无依据的防御代码和重复验证。
- 当前只记录草稿，继续讨论；不得把本次记录理解为立即实施所有重构和权限变更的授权。

## 拟采用的工作流

开发流程：工作分支完成实现 → 相关本地验证与开发 CI → PR → 用户确认合入 main。

发布流程：从已通过所需开发检查的版本提交选择发布标签 → 构建安装包 → 检查必要的产物与启动行为 → 上传资产及更新信息 → 正式发布。

版本号在开发检查之前确定，标签指向受检提交。正式发布自动构建或复用已有产物的具体方式在实施时确定；不把“绝不重新构建”或“发布绝不运行测试”立成新教条。检查必须有具体用途和结束条件。

| 现有入口 | 拟调整职责 |
| --- | --- |
| `.github/workflows/test.yml` | 恢复 PR 和主分支开发反馈；复用有效的行为、依赖和装配检查，按实际影响触发 |
| `.github/workflows/release.yml` | 连续完成版本校验、构建、必要产物检查和正式分发 |
| `.github/workflows/publish.yml` | 旧晋级工作流退役，必要分发动作并入 release.yml |

限制代理无依据重跑，与允许正常开发 CI 是两回事。拟替换当前“CI 只能作为最后验证”的仓库政策；实施时须同步处理其文档和工作流接线，不允许只改名称而保留原串行负担。历史失败记录不得清零或改写为通过。

## 拟整体撤下的旧机制

- 每个新候选固定执行 26 项人工核心验收的默认发布要求。
- 基于文件路径自动扩张到完整人工验收目录的候选计划。
- 验收 JSON、签字字段、验收记录提交编号，以及依赖它们的晋级状态机。
- 只服务于以上机制的脚本、专用测试和规则入口，包括 `release-plan.mjs`、`check-release-acceptance.mjs` 的对应职责。

保留历史记录。保留真实产品回归验证，以及版本、资产、签名、更新信息等实际分发检查；不能借清理删除有效缺陷复现、隐瞒失败或改变用户要求。旧体系退役不等于测试库整体重写。

## 开发验证与成本控制

- 先完成产品实现，再准备必要的定向验证。已有有效检查足够时复用，不为了本次任务再建测试框架。
- 本地验证聚焦原故障和此次行为；开发 CI 承担自动回归和相应平台检查，不要求本地完整复制远程矩阵。
- 依赖、资源、运行时和打包配置发生变化时，在开发阶段验证真实装配路径；避免只测源码，直到发布才第一次尝试打包。
- 验证尽量经过实际装配和用户调用入口，避免大量 mock 或内部细节断言造成虚假的可靠感。
- 文档和治理记录不决定产品是否可发布；文档改动不默认触发产品构建。
- 人工观察聚焦本次确实涉及、自动化无法观察的行为，不默认重新验收整个产品。
- 相关验证通过后结束。新增实验须能回答一个具体未解决的问题，不能因提交、推送或代理“不放心”而重复通过的检查。
- 失败按所在步骤处理。上传失败不默认重新编译；产品失败回到对应产品修复；不得原样重跑整个交付链。

## 防止 AI 擅自降级与扩大范围

文字规则和另一个模型评审都不能保证 AI 永远正确。拟采用的实际边界是：AI 提出修改，用户决定是否接受，自动化负责合入后的执行。

拟实施的权限措施仍需确认具体配置：AI 使用独立受限身份；管理员凭据与 AI 运行环境隔离；保护 main、必要检查和涉及验收标准的关键文件；AI 不得批准自己的修改、修改保护设置或直接发布。仅切换 token 而仍能读取管理员凭据，不构成隔离。

PR 审阅直接对照用户原始需求和实际 diff，重点查看功能删减、默认行为改变、失败被静默吞掉、断言弱化、skip 扩大，以及无依据的新配置、重试、兜底和抽象层。AI 重写后的描述不能替代原始需求。无法完成时应明确报告未完成。

只保留一次有明确目的的合并确认，不恢复多轮代理审批、签字表和发布验收平台。权限保护能阻止未获批准的合并，不能自动判断所有语义降级或过度设计。

本次讨论中的只读检查发现：GitHub CLI 身份具有管理员权限，main 未配置分支保护，规则集查询未列出规则。此为当时快照，实施前重新核对；目前未改变设置。

重构的实际结果应当是：开发者能从相关文档找到负责代码和必须保持的行为；普通修复在同一个 PR 中完成相关验证；无关的文档手续不再阻塞产品交付；合并上游时仍能识别和保护桌面差异。减少文件或测试数量本身不算完成。
