# Decision: Unified repair and regression gating for vendored-plugin contract drift after upstream 0.1.7

Status: implemented

[中文](2026-09-25-vendored-plugins-017-contract-drift.md) | English

## Problem

The 0.1.7-rc.2 upstream merge introduced two new contracts, and each vendored first-party plugin missed a different piece. First, the Loader gained a compatibility gate that validates every plugin's `@deepseek-ai/dsh-*` peerDependencies against the runtime version; `dsh-whale` and `dshbot` still pinned exact `0.1.5-rc.2`, so their optional rows were silently disabled via warn-and-continue — the live failure that blanked the Whale settings slot and left plugin routes unmounted. Second, `SettingsForms` removed `register`/`get` and renamed `settings/updated` to `settings/document-updated` with a payload reduced to `(ns, revision)`; `dsh-usage-panel`'s price-record path therefore warned every scan with its repair/import path dead-locked, and `dshbot`'s catalog registration threw `settings.register is not a function`, leaving the whole row inactive. The upstream merge shipped with no regression coverage over vendored manifests or settings-API usage, so drift only surfaced through user reports.

## Decision

Widen the peer pins in `vendor/dsh-whale` and `vendor/dshbot` to `^0.1.5-rc.2` (which covers the rest of the 0.1.x line under the gate's `includePrerelease` semantics), and add desktop-suite regressions that run the vendored `app-boot`'s real `evaluatePluginCompatibility` against both manifests. Port `dsh-usage-panel`'s settings access to the new model: reads via `describe()` (ns is the profile entry id; the value projects volatile fields), writes stay on `update`, and the `document-updated` listener re-reads instead of consuming a payload value; test fakes adopt the same shape. Diagnosis uses a production-equivalent `dsh web` spawn (junction plus the full `--patch` overlay set) to observe activation directly rather than inferring statically.

The landed `dshbot` catalog shape: the seven catalog fields become `.volatile().hidden()` fields on the plugin's own `Config`, so `describe()` projects them as namespace `dsh-bot` (the Loader insert id) and reads, revisions, and `document-updated` invalidation all work natively. Writes cannot go through `settings.update` — `configEditor.edit`'s consistency check composes only profile-local layers, so an overlay insert is invisible and the write is refused (observed live: `Configuration for "dsh-bot" is overridden by a home patch or command-line overlay`). Instead `catalog-scope` atomically writes `$DSH_HOME/dshbot-catalog.json` (tmp+rename, counter-suffixed tmp names avoid same-millisecond collisions), then commits the fields in place via `entry.update({config})` through the Loader's volatile-only path (`equalExceptVolatile` + `_commitVolatile` — no remount, no profile patch), and one `describe()` pass publishes the invalidation. On activation an `internal/status` hook restores the file, then runs the blob-avatar migration; a corrupt restore input (bad JSON, schema rejection, valid-but-non-object) is quarantined as `dshbot-catalog.rejected-*` for evidence while boot continues on the default catalog instead of warning forever. Client writes move off `remote.settings.mutate` onto the plugin's own `/dshbot` RPC (`catalog/items`, keeping `checkRevision` CAS and the `{view}` receipt, plus an explicit array check on `items` — the schema's `.default([])` would otherwise flatten a missing value into a table-clearing write).

Acceptance testing on the real desktop caught three more 0.1.7 contract drifts and one persistence gap, fixed in the same batch:

- The client-side `settingsScope` service is gone (only stale build output remains): the dshbot client inject hung and its module never applied. Rebound to `configForms` — `configForms.get('dsh-bot')` returns a `ConfigForm` (`getSnapshot`/`subscribe`/`mutate`) and `configForms.describe().acceptView()` folds write receipts; the surface is isomorphic to the old one. The host `describe()`'s `volatileForm(schema)` only projects fields under volatile ancestors, so the `dsh-bot` row's value/schema envelope matches the seven catalog fields and `decode()` validation passes.
- `uiSession.pendingInteractions` was renamed to `sessionStatus` (`Map<SessionId, SessionStatus>` with `status.pendingInteraction`): dshbot's fallback returned a fresh `Map` per `getSnapshot`, so `useSyncExternalStore` looped forever (React error #185) and BotPage crashed on mount. The projection memoizes by source-snapshot reference to keep snapshots referentially stable.
- `connection.rpc.handle` is a dead-end API for plugin callers: `get rpc()` captures the connection plugin's own ctx and `handle` mounts through `owner.webServer.register` — that owner's inject list lacks `webServer`, so any external caller throws `cannot get property`. The `/api` interceptor slot is already owned by gateway. Instead dshbot mounts its `/dshbot` prefix route itself via `webServer.register` on a `ctx.inject(['connection','webServer'])` child ctx, gates requests with `connection.admit` (Host/Origin + browser auth), and locally reimplements the `client-request`/`server-response` envelope codec with `checkRevision`.
- Every `configEditor.edit` (any settings write) and patch-HMR pass runs `reconcileProfilePatches`, re-applying all layers: the dsh-bot overlay row carries no catalog keys, so the volatile commit resets the seven fields to defaults — any settings write wiped the live catalog. The fix listens for fiber-filtered `loader/volatile-update` (`Context.filter` scopes to `owner.fiber`), distinguishes own commits via a `committing` flag, and asynchronously reseeds from the persisted file on external resets. An earlier attempt patched external update candidates through `internal/config` — that waterfall is global, so the callback ran on other fibers and would have leaked catalog keys into every plugin's config resolution; it was removed. The wipe→reseed path has a regression test.

## Alternatives considered

- Keep moving peer pins to each new exact version: the next rc breaks everything again and produces no regression signal.
- Persisting the dshbot catalog via `settings.update`/`configEditor.edit`: overlay rows are refused by the consistency check (reproduced live), and even if writable, a high-churn catalog would amplify into profile-patch writes plus Loader reconciliation — unusable. The landed shape keeps Config volatile fields for projection while writes bypass ConfigEditor.
- Static grep instead of live activation checks: inject-name resolution, optional-row disabling, and stale-session scan skips only surface under a real Loader run — the dshbot `register` crash, the `settingsScope` hang, and the React #185 loop were all missed by static scanning and caught by live reproduction.
- Patching external update candidates through the `internal/config` waterfall: that callback dispatches globally (`this.fiber` is not dsh-bot's), so it would inject catalog keys into every plugin's config resolution — a leak larger than the benefit; dropped in favor of `loader/volatile-update` reseeding.

## Consequences

All built-in rows pass the compatibility gate and activate under 0.1.7-rc.2, and `dshbot`'s catalog write roundtrip is verified live end to end (UI bot creation → `/dshbot` RPC → atomic persist → restart restore → reseed survives reconcile wipes → UI delete writes back); Whale settings fields and the usage-stats billing write path were verified on the same pass. `dshbotEnabled` (default off) still gates the mount; when off, the overlay is stripped while the catalog file and bot sessions are preserved. Any future peer-pin drift after an upstream merge fails `npm test` immediately. The live spawn diagnostic becomes the standard tool for auditing vendored drift.
