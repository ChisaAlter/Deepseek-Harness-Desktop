# Decision: 桌宠原生区域限定到绘制表面

Status: implemented

中文 | [English](2026-09-29-pet-native-regions.en.md)

## Problem

桌宠使用整块显示器大小的透明置顶窗口。切成可交互时，整窗接收鼠标；渲染器忙碌而尚未处理退出事件时，下层应用点击会被吞掉。另外，角色、聊天卡和菜单的命中盒取外接大矩形，把表面之间的透明空白也当成交互区。回归测试已复现后者。

既有记录审计：[真实绘制几何](2026-09-24-whale-hover-bubble-geometry.md)部分重叠，保留身体变换、气泡锚点和拖拽守卫；本次补上原生区域边界和分离表面命中。[主题透明背板](2026-09-29-pet-theme-transparency.md)处理不透明填充，是另一条故障路径，继续保留。proposed/rejected 中没有相同原生区域决定。

## Decision

Windows/Linux 通过既有、校验 sender 的交互 IPC 上报独立绘制矩形，主进程验证有限数值、限制数量、取整并裁到窗口边界，再用 `setShape` 设置原生区域。绘图坐标仍覆盖单显示器，避免恢复逐帧移动透明窗口的闪烁问题。区域包含角色、投喂、粒子、气泡、状态卡、聊天卡和菜单阴影；几何不变不重复发送或设置。初始空区域使用一个零面积矩形，不能用会恢复整窗的 `setShape([])`。macOS 不调用该 API。

鼠标命中及退出迟滞按各交互表面的最短距离计算，不把透明空隙填成大矩形。显示和恢复使用 `showInactive`，仅显式打开聊天卡取得输入焦点。保留既有角色悬浮行为、主题透明保护和显示器坐标模型。

## Alternatives considered

- 仅缩短鼠标轮询：实现简单，但忙碌渲染器退出前整屏仍会接收点击，表面间的大命中盒也仍在。
- 每帧移动小窗口：原生外框天然紧凑，但会重新引入本项目已记录的 Windows 透明分层窗口移动闪烁，并重做拖拽与跨屏坐标。
- 关闭全局后台节流：可能缓解某些页面停刷，但没有消除透明输入遮挡，还扩大整应用持续渲染开销。

## Consequences

透明空隙不再属于宠物原生窗口，即使交互退出滞后也能点击下层应用。变化帧需要传输少量矩形并更新原生区域；未来新增绘制源必须登记墨迹边界，避免裁切。macOS 仍依赖窗口穿透开关，未认证原生区域隔离；本次也不能证明所有主页面加载问题均由此导致。

定向回归覆盖分離表面、区域验证/去重、关闭卡片和非激活显示。Windows 实机脚本与证据位于 [窗口区域验收](../../../qa/results/2026-09-29-pet-window-regions/verify.cjs)，使用实际管理器、THA4 渲染器与 Win32 区域查询。
