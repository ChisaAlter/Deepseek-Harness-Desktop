# Decision: 提交前告警超出托管上限的大文件

Status: implemented

中文 | [English](2026-09-22-large-file-commit-warning.en.md)

## Problem

GitHub 拒绝单文件超过 100 MiB 的推送。用户在工作区放入大产物（构建输出、模型权重、录屏）后，提交对话框只列出路径与增删行数，看不到字节数，于是「Commit, push & PR」会一直走到 push 才失败；失败点离原因很远，且此时大文件已经在本地历史里。对话框需要在不改变提交语义的前提下，在用户点下提交前告诉他是哪个文件、多大。

## Decision

主进程新增 `gitCheckLargeFiles(cwd)`：对 `git status --porcelain=v1 -z --untracked-files=all` 给出的路径取 `lstat` 尺寸，返回严格大于 100 MiB（`100 * 1024 * 1024`）的 `{ path, size }` 列表。它只读元数据：不调用 `git add`、不写索引，因此打开对话框不会把用户没打算提交的内容留在暂存区；用 `lstat` 而非 `stat`，符号链接不跟随；忽略项由 `git status` 天然排除；重命名记录取 git 给出的目标路径。

路径按仓库根解析：`--porcelain` 即使从子目录调用也输出仓库相对路径，所以用 `rev-parse --show-prefix` 从已授权的 cwd 反推出仓库根，而不是再信任一个来自 git 输出的新根。反推出的根若本身已授权就扫描整个仓库（对齐从子目录执行的 `git add -A` 会暂存整棵树的行为）；未授权则只扫描已授权的 cwd 子树，其上的候选路径跳过。列出的路径在 `status` 与 `lstat` 之间消失时跳过，不报错。

客户端在提交对话框打开时发起一次扫描，并做两件事：把结果收窄到本次提交真正包含的路径（用户排除的文件撤下其警告；未跟踪目录在对话框中折叠成 `dir/`，其下命中的路径按前缀匹配），以及在对话框关闭时作废在途结果，避免旧答案描述新一次提交。扫描失败按「无警告」降级，不阻塞提交。

## Alternatives considered

- **在 `gitStatus` 里顺带返回尺寸**：省一次 IPC，但状态读取是标题栏常驻轮询，会让每次刷新都多 stat 一遍全部改动文件；而警告只在对话框打开时需要。
- **直接把文件加入 `.gitignore` 或改用 LFS**：超出工具职责，会在用户不知情时改变仓库策略。
- **在 push 失败后解析远端报错再提示**：报错文案随远端变化，且用户此时已产生本地提交，修复成本已经付出。
- **跟随符号链接判断目标大小**：链接可以指向工作区外，既会读到无关文件，也会对连接点大小给出误导性警告。

## Consequences

对话框现在能在提交前列出超限文件及其大小，用户可先取消、排除路径或改走 LFS。行为边界是只警告不改行为：按钮仍可点，提交语义不变。阈值按 GitHub 的二进制上限取 100 MiB（104,857,600 字节），而不是十进制 100 MB；因此用户若按十进制理解，94.3–100 MB 的文件会触发警告，这是刻意的保守方向。诊断信息只含仓库相对路径与字节数，不读文件内容。
