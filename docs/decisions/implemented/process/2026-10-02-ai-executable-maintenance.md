# Decision: 维护准则改写为 AI 可直接执行的形式

Status: implemented

## Problem

[维护准则](../../../maintenance/README.md)的主要读者是 AI 代理，但旧版大多是抽象原则和成串的禁止句，缺少触发条件和例子，代理容易按字面误用或漏用。项目经常合并上游，准则却只有合并原则：没有可照做的步骤，没有从上游改动推出验证范围的方法。准则还规定上游差异记在功能卡里，但当时没有一张卡这样记录，实际起作用的差异索引是 `harness-desktop-forks.js`。

另有三处需要澄清：诊断时执行已有命令与新编写复现测试的边界；其他代理不可见的 Codex 本机规则与仓库规则的职责；主要给 AI 阅读的英文配对带来的双侧维护成本。“实现完成前不写测试”与“修复后保留复现”可以顺序执行，并不矛盾。

## Decision

- 准则开头增加“触发 → 动作”速查表，末尾增加常见错误对照表；正文保留权威、阶段、证据、风险选择和 CI 停止规则，并把会变的当前事实（核心场景数量、Node 钉版迁移、线上工作流迁移状态、hook 细节）移回发布操作说明和 CONTRIBUTING，准则只链接。
- 保留原开发顺序：诊断阶段读取日志、执行已有命令或直接观察；新增测试、复现用例或脚本、夹具、验证工具和 CI 准备均放在实现完成后。取消初稿的最小复现例外，并同步发布操作说明；修复后可用旧版或受控缺陷对照证明复现有效。
- 上游合并一节增加 DSH 合并步骤、冲突裁定和按实际影响选择的验证表。先确认两端提交对象可读取，缺失时从实际来源获取并核对身份；pin 文件不保证本地有 Git 对象。预演输出用于理解本地差异、合并结果和文本冲突；上游增量单独比较旧上游 SHA 与目标 SHA，再与本地差异和消费者对照。差异分两层：行为契约在功能卡，DSH 树的位置索引是 `harness-desktop-forks.js`，其他来源用各自的 `DESKTOP-FORK.md`。文档同步不自动触发产品安装、构建和启动；已有同源码、同 profile 产物可用于消除重复构建，必要行为与类型检查仍执行。
- 防御代码、检查和门槛的依据包括明确需求、已观察故障或当前契约要求的边界；无需等事故发生才实现已要求的权限等边界。与这三项均无关的假想防御不增加。
- 删除准则、AGENTS.md 和发布操作说明中对本机 Codex 全局约束的引用。
- 停用准则的英文配对：删除 `README.en.md` 和确认记录，移出 `scripts/i18n-pairs.manifest.json`，英文文档改为链接中文准则。

## Alternatives considered

- 只修补措辞、保留原结构：改动小，但速查入口、合并步骤和验证选择仍然缺失，不能解决经常合并上游时的重复摸索。
- 把位置索引改成功能卡里的文件清单：和 `harness-desktop-forks.js` 重复维护同一事实，而且后者已经接入测试，因此不采用。

## Consequences

准则增加可直接查找的执行入口；开发顺序、冲突裁定、CI 次数和证据边界保持原要求。验证由实际风险触发，避免借上游同步恢复固定重检查链。

vendor 内 AGENTS 和测试文档中的“Complete implementation before preparing tests”保持原义，与仓库和 Codex 现有开发顺序一致。项目要求在仓库中完整说明，其他代理不需要读取 Codex 本机配置。功能卡的 `Upstream differences` 一节仍在触及相关功能时逐步补齐，不做一次性改造。位置索引注释里的功能卡 id 同样在新增或迁移标记时补写。

本次只改文档和配对清单，不涉及产品代码，因此没有启动产品、打包或跑 CI。验证限于维护结构检查和受影响配对的确认；它们只证明引用和结构一致，不证明新规则的执行效果。效果要从后续合并和修复中的实际漏检与重复劳动来观察。
