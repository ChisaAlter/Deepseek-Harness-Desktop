# Decision: 启动器独立分发架构（双线路、独立增量包与组件平台）

Status: proposed

中文 | [English](2026-09-24-launcher-standalone-distribution.en.md)

## Problem

现有启动器与完整 DSHD 共用同一 Electron 进程、appId、安装目录与 Setup：它不能在自身常驻时可靠地覆盖安装桌面端，也没有承载可选工具/服务的边界。分发只有 GitHub 一条线路，国内网络下检查与下载没有兜底；每次升级经 `downloadFile` 拉完整 Setup，虽已接入 electron-updater blockmap 差量（[2026-09-17](../../implemented/product/2026-09-17-electron-updater-differential-updates.md)），但那是已安装应用的自更新通道，无法作为启动器对外分发的独立增量制品。Gitee 的附件容量、匿名下载与 Range 行为在本项目尚未实测。

## Proposal

把现有启动器重构为独立轻量产品并承担分发职责，按 `docs/superpowers/plans/2026-09-24-launcher-refactor.md` 的批次执行：

1. **唯一界面原地重构**：`src/renderer/launcher.*` 保留五个分区与 Recovery Board，且保全是能力级——桌面端启停（启动/停止/跳过用户插件启动/完整重试）、版本管理（安装识别、正式版列表、指定版本安装切换、卸载入口）、插件排查（名单、归因、逐项开关、批量禁用、移除）、数据导入与启动器设置逐项保留并可操作。先在同进程内提取启动器应用服务与安装探测边界，再拆 DSHD 运行时装配，使启动器在未安装桌面端时也能运行并完成安装。跨进程后桌面运行时经带版本、本机认证与请求身份的窄接口服务启动器，恢复与插件排查逻辑不复制。
2. **双程序身份**：Launcher 有独立 appId、安装目录、卸载记录与单实例锁；DSHD 桌面端仍由完整 NSIS Setup 安装，离线完整包永远可用。已安装用户的设置与 `dsh-home` 不丢失；身份与迁移细节随打包边界落地时验证，不继承任何未落地原型。
3. **双线路同一字节**：每次候选构建只生成一套完整 Setup；GitHub 与 Gitee 镜像相同文件。签名清单绑定目标版本、候选 SHA、资产大小与 SHA-256、增量基线、平台架构、最低 Launcher 版本及两条镜像 URL，是唯一版本权威；离线私钥签名、客户端内置公钥。选择 Gitee 后查询与下载不暗中请求 GitHub。
4. **独立增量包**：以固定上一正式版 Setup 为基线发布 `from→to` 补丁；客户端离线重建目标完整 Setup，长度与 SHA-256 核对通过后才运行安装器；缺基线、补丁损坏或无收益时回退同目标完整包。与 electron-updater blockmap 分层共存：blockmap 继续服务已安装应用的自更新，不冒充独立增量包。
5. **组件平台**：首批仅项目审核并签名的工具/服务；组件为独立进程，二进制进启动器自有版本目录、数据进独立目录，原子切换与回滚；组件操作锁与 DSHD 安装锁分离；服务运行时关窗进托盘、退出停服务。不写 `dsh-home` / Harness profile，不复用插件市场。
6. **slim 能力边界**：轻量包不含 vendored `dsh plugin` 工具链——依赖它的操作（插件移除、导入页插件重装）在 slim 下统一显式返回 `desktop-only` 并在 UI 标注「需在桌面端内操作」，而不是深处在 spawn 失败；插件禁用/启用属配置写盘，slim 仍可执行，写盘后由运行时下轮启动生效。移除插件仅在卸载成功后清 `disabledPlugins`，失败必须保留禁用态，不得把崩溃插件静默放回。

## Alternatives considered

- **保持单应用、仅给 `index.js` 加 launcher-only 开关** — rejected：顶层仍导入 Harness、市场、宠物与远程，证明不了轻量边界；且单进程无法在自身常驻时可靠覆盖安装自身。
- **新建第二套启动器再迁移旧功能** — rejected：产生两套 UI 与重复入口，旧功能被推迟；用户明确要求重构现有界面。
- **把 blockmap 改名为增量包** — rejected：它依赖 `latest.yml`、旧缓存与当前版本，不能作为固定 `from→to` 制品供离线重建与核验。
- **GitHub 与 Gitee 各自构建发布** — rejected：同版本不同字节会让缓存与增量基线失效；发布权威必须只有一个候选构建。
- **开放第三方组件或脚本入口** — rejected：组件是可执行代码；首发缺少多发布者信任根与隔离合同，先限项目签名组件。

## Acceptance criteria

- 五个分区与恢复能力保留；源码、已安装、未安装、失败恢复、托盘重开只出现一份启动器界面。轻量包剔除 Harness 归档与桌面插件，并实测体积与启动时间。
- 同一候选 SHA 的两镜像完整包与增量包字节哈希一致；签名清单可验证，篡改、回放旧序号与跨源错配被拒。
- 用已验证基线 Setup + 增量包重建的目标 Setup，长度与 SHA-256 与同候选完整包一致；基线不符或补丁失败自动回退完整包。
- 未安装环境从启动器选线路、下载、校验、安装并进入 DSHD；首装、更新、取消、断线、重启均不破坏可运行的旧版本。
- 工具与服务组件各一例在真实 Windows 完成安装、运行、关窗驻留、停止、更新、回滚、卸载。
- Gitee 线路在真实同量级附件、匿名下载、国内网络与哈希复核通过后才对用户开放；Range 不可用时禁用断点续传。

## Risks

签名私钥与 Gitee token 需独立保管，不入仓库或客户端。压缩后的 Setup 增量收益可能低，须用真实相邻版本测量体积、重建时间与磁盘峰值。拆进程涉及 IPC、配置与生命周期迁移，窄接口必须保留认证与恢复能力，不能靠隐藏窗口代替接线。Gitee 附件限制未实测，可能迫使线路能力降级（如不支持 Range 续传）。
