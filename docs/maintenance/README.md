# WhaleIsle 维护系统

本文件是 WhaleIsle 唯一的项目维护准则，适用于整个仓库及所有 vendored 子项目，主要读者是执行维护的 AI 代理。目标是让修改正确完成、缺陷可以复现、交付可以追溯，同时控制维护成本。文档、测试、门禁和 CI 的数量不算进展。

WhaleIsle 是当前项目名称；仓库目录、技能路径和运行时标识里的历史名称只是技术标识。

## 速查：触发 → 动作

遇到下列情形，直接执行右列动作。细节见后文对应章节。

| 触发条件 | 动作 |
| --- | --- |
| 开始任务或恢复上下文 | 读相关功能卡和手册章节；写明目标、环境、负责模块、期望结果和直接观察方法 |
| 修 bug，且故障可以直接观察 | 读取日志、使用已有命令或直接操作确认现象；完成修复后再编写必要复现并验证 |
| 实现还没完成 | 集中诊断和实现；测试用例（含最小复现）、QA 夹具、测试框架和 CI 配置的准备留到实现完成后 |
| 想加兜底、重试、兼容分支、抽象层或配置项 | 指明明确需求、已观察故障或当前契约要求的边界；至少具备一项具体依据，否则不加 |
| 想新增检查、门禁或流程要求 | 先回答「新增门槛与防御代码」一节的五个问题；答不出就复用现有入口 |
| 测试失败或耗时太长 | 保留断言和覆盖；先把失败归类为 product、tool、environment 或 unknown |
| 同一失败第二次出现 | 停止原样重跑；写清未解问题、要改变的条件，以及结果如何区分不同解释 |
| 结果是 Skip、Blocked 或 Not run | 报告为未通过并写明原因；不写成 Pass |
| 必要验证缺环境或前置条件 | 先尝试补齐；补不齐就标 Blocked 并说明缺什么；缩小必要范围需要用户明确决定 |
| 只改文档、导航或翻译 | 只核对改动的引用、当前事实和已有配对；不启动产品，不打包，不跑 CI |
| 改动涉及 UI、窗口、安装、权限或文件保存 | 做真实操作并观察结果；快照、mock 和窗口属性不足以放行 |
| 准备触发 CI | 确认同一 SHA 的本地必要项全部 Pass，并核实累计未通过次数；见「失败、重复与 CI 次数」 |
| 合并上游 | 按「上游合并与差异保护」的步骤执行；Git 无冲突不代表没有语义冲突 |
| 上游冲突会删减能力、改变交互或默认值、改变数据或权限 | 列出可行方案、收益损失和建议，交用户决定 |
| 发现自己违反开发顺序、提前跑 CI、削弱检查或报错结果 | 停止相关动作，回到最后有证据的状态并如实更正；不自行回滚用户数据 |
| 汇报完成 | 实现完成和验证完成分开报告；列出运行过、失败和跳过的检查 |

## 权威与职责

用户当前的明确要求优先。本文件独占维护顺序、验证选择、成本限制和停止规则。[发布操作说明](../handbook/modules/release-process.md)在本准则下细化候选身份、验收数据和晋级操作，不是另一套准则。AGENTS、CLAUDE、技能、rules、功能卡、旧决定和上游指南只做定位，不能追加审批、测试阶梯、数字指标或自动执行要求；发现冲突时在负责位置修正它，不两套叠加执行。

上游的产品、架构、持久数据、权限和实际装配契约继续有效；它们的维护惯例和历史门槛只作背景。未修改的上游来源、历史计划和封存记录保留原貌，其中的“必须”不会恢复旧规则。清理不能削弱断言、扩大 skip 或抹掉失败。

| 维护位置 | 唯一职责 | 何时更新 |
| --- | --- | --- |
| [功能卡](../features/README.md) | 用户路径、长期不变量、负责模块、验证入口和上游差异的行为契约 | 契约或最近相关验证改变 |
| [手册](../handbook/README.md) | 当前架构、实现入口和实际操作 | 实现或操作改变 |
| [差异位置索引](../../src/shared/harness-desktop-forks.js) | DSH 树中桌面差异的位置和结构标记 | 新增、迁移或删除对上游文件的修改 |
| [决策](../decisions/README.md) | 长期取舍及理由 | 架构、兼容性、格式或长期流程改变 |
| [复盘](../postmortem/README.md)、已有 issue / QA | 系统性故障、漏检原因和纠正效果 | 反复、昂贵或系统性事故 |
| AGENTS、技能、rules | 定位提示和统一流程入口 | 导航或责任改变 |
| 现有测试、检查脚本、工作流 | 对具体失败作可执行判断 | 已证明漏检或当前契约要求 |
| [配对工具](../i18n/README.md) | 已登记双语文档的结构和确认摘要 | 配对内容改变 |

每个事实只有一个负责位置，其余位置链接它。普通修复用提交或 PR 加已有行为证据，不强制提案、决策、复盘三件套。新内部记录用单语。Allowed touch 用来定位负责代码，不是审批边界。历史记录保留原结果，不因新流程改写为通过。

## 阶段与完成条件

| 阶段 | 执行内容 | 结束条件 |
| --- | --- | --- |
| 定位 | 读取契约、代码和日志，使用已有命令或直接操作观察故障 | 目标、环境、负责模块、期望结果和直接观察方法明确 |
| 实现 | 完成需求或根因修复，更新受影响的当前事实 | 实现范围稳定 |
| 本地验证 | 准备并执行必要测试、构建和真实操作 | 原失败和受影响路径通过，必要边界没有缺口 |
| 最终 CI | 同版本本地必要项全通过后，手动派发 | 精确源码的最新必要 job 成功；失败先回本地查漏检 |
| 候选验收 | 对正式原包验证身份、安装、核心集和影响集 | 该包的必要结果、缺陷和真实放行完整 |
| 晋级与反馈 | 发布原始字节；出现漏检时修正负责模块的覆盖 | 资产身份一致；修复效果和遗留问题如实交接 |

**诊断和测试准备的边界。** 定位阶段可以读取源码和日志、执行已有诊断命令或直接操作产品来观察故障。新增复现用例、复现脚本或测试断言，即使只有一条，也属于测试准备，放在实现完成之后；不因命名为“最小复现”或“诊断”改变顺序。实现完成后，编写必要的定向复现并保留；能在旧版本或受控缺陷上对照时，证明它能发现原故障，再核对修复版本通过。“先完成实现”与“保留防复发复现”按此顺序执行。

简单任务用简短说明。复杂任务维持一份现有状态记录：目标和范围、版本和环境、实际结果、未解决原因、下一步、累计 CI 次数。不另建执行平台或重复台账。

## 证据类型

| 证据 | 覆盖的风险 | 不能推出的结论 |
| --- | --- | --- |
| 维护结构 | 引用断裂、配对过期、记录格式和归档损坏 | 语义一致、翻译准确、产品正常 |
| 模块行为 | 输入输出、原缺陷、当前契约边界和相关集成 | 安装版或系统交互已经通过 |
| 工程装配 | 类型契约、依赖和锁文件、原生模块、包内闭包 | 用户实际操作成功 |
| 实际环境 | UI、命令、文件保存、安装、权限、系统状态 | 未测试的平台和不同前置状态通过 |
| 交付身份 | 源码、CI、候选、摘要和原包晋级的对应关系 | 人工观察真实发生，或签字人确实获授权 |

每项结果绑定实际版本和必要环境；有相关改动后只重做失效的那部分证据。状态分 Pass、Fail、Blocked、Skip、Not run，后三种不算必要项通过。进程退出 0、测试文件存在、以前的绿色结果、mock 或静态属性，都不能单独证明真实路径。要查看所需场景实际执行的结果；需要 live 的工具使用严格入口（如 `--require-live`），窗口合成检查不能用状态检查代替。

## 按风险选择验证

| 修改类别 | 必要本地验证 | 不自动追加 |
| --- | --- | --- |
| 文档、导航、翻译 | 改动的引用、当前事实、已有配对；双侧核对后更新摘要 | 产品启动、打包、全量产品回归、CI |
| 维护脚本、工作流、QA 观察器 | 合法输入和实际坏输入的行为检查，必要的真实命令或 hook 接线 | 产品安装或新候选；观察器改动不自动扩大产品场景 |
| 普通产品修复 | 原故障的直接验证、相关行为和当前契约边界 | 无关模块、全库 lint、全表验收 |
| UI 与系统交互 | 相关模块检查，加真实窗口或操作观察 | 只靠快照、mock 或窗口属性放行 |
| 安装、运行时、依赖、持久数据 | 正确 profile 构建、锁与闭包、真实安装或升级、真实数据路径 | 用源码 smoke 代替安装器 |
| 上游合并或共享底层变化 | 按「合并后验证选择」表 | 每改一点就重复完整构建 |
| 正式新候选 | 发布操作说明定义的核心集加影响集；交付 DMG 时才要求 Mac 实机 | 文档或报告更新后重新打包；旧包的 Pass 自动继承 |

说明验证选择时，指出具体风险和对应方法即可，不必每次填整张表。必要范围来自用户要求、已观察到的故障和当前契约。代理不能因为耗时、环境不便或 CI 更干净而自行豁免。

## 新增门槛与防御代码

新增任何门槛、检查或防御代码前，先回答：

1. 它针对哪项明确需求、已观察故障或当前契约要求的边界？
2. 现有实现或检查缺少什么，为什么不能直接复用？
3. 它属于哪个负责模块？
4. 什么时候执行，结果怎么判断？
5. 什么时候移除或调整？

依据不足就不新增，优先复用现有入口。明确需求和当前契约要求的边界无需等事故发生才实现，例如已要求的权限隔离应落实权限校验；与需求、故障和契约均无关的假想兜底、重试、兼容分支、抽象层或配置项不增加。测试便利不是提前改造产品架构的理由。已有必要检查不因失败或耗时被删除；清理前先证明覆盖重复或契约已经改变。

## 上游合并与差异保护

WhaleIsle 经常合并 DSH 和其他来源的上游更新。保护对象是已交付的用户能力、缺陷修复、数据兼容、权限边界和明确裁剪的行为；文件名、旧实现和 fork 标记只是定位线索。上游更新不授权覆盖本地差异，保留旧代码也不是拒绝等价上游实现的理由。

### 差异记在哪里

- **行为契约**：记在负责的[功能卡](../features/README.md)里。有长期上游差异的卡加 `Upstream differences` 一节，写保护行为、差异理由、来源基线和验证证据，可在下次触及该功能时补齐。
- **位置索引**：DSH 树中的桌面差异登记在 [`harness-desktop-forks.js`](../../src/shared/harness-desktop-forks.js)。`DESKTOP_PACKAGES` 是桌面自有包，`COMPOSITION_ROWS` 是装配行，`FORK_FILE_MARKERS` 是对上游拥有文件的修改。新增或迁移对上游文件的修改时，同步更新对应标记，并在注释里写明负责功能卡 id。标记只证明结构还在，不证明行为正确。
- **其他来源**：各 vendor 树的 `DESKTOP-FORK.md` 记录来源仓库、基线和差异；[vendor 索引](../../vendor/README.md)列出全部来源。
- 卡片或标记缺失不代表差异可以删除。合并时遇到未登记的差异，先查源码、历史和实际行为，再补到最近的负责卡；不要求每次合并都全库盘点。

### DSH 合并步骤

1. **确定目标与对象前提。** 记下实际来源仓库、目标 ref、解引用后的完整 commit SHA 和本地起点；旧基线读 [`vendor/harness-upstream.json`](../../vendor/harness-upstream.json)。确认旧基线与目标提交对象在本地可读取；缺失时从已确认的来源获取对应 ref，并核对完整 SHA 后再预演或比较。pin 文件只记录身份，不保证 Git 对象存在；旧基线无法取得时报告缺失并阻塞该合并，不改用其他版本代替。
2. **准备工作树。** `sync:harness` 要求整个工作树干净。有未提交改动时停下，请用户决定是否先做快照提交；不 stash、不 reset、不丢弃用户或其他任务的改动。
3. **预演。** 运行 `npm run sync:harness -- --dry-run --ref <ref> --sha <sha>`，检查合并能否完成及文本冲突。脚本会输出旧 pin 与当前 vendor 树的差异；无冲突时还输出候选合并树与当前树的差异。这些输出不是完整的上游增量。
4. **影响分析（只读）。** 预演取得并校验目标对象后，在仓库根分别用 `git diff --name-status <旧SHA> <目标SHA> --` 获取上游增量，用 `git diff --name-status <旧SHA> HEAD:vendor/deepseek-harness --` 获取已提交的本地差异。按这两份差异及位置索引定位交集，处理重命名两端，再沿接口、生成产物（slot catalog、第三方声明）、`*.patch.yml` 挂载和配置消费者追踪间接影响。每个交集都定位到负责功能卡；无冲突的变更也纳入分析。上游带回的 AGENTS、hooks、Node 钉版、测试或发布默认值也列入清单，按本准则处理，不能借同步恢复旧门槛。
5. **合并。** 运行 `npm run sync:harness -- --ref <ref> --sha <sha>`。有冲突时脚本在隔离 worktree 里停下：按「冲突裁定」表逐个解决，`git add` 后运行 `npm run sync:harness -- --continue`；要放弃就运行 `npm run sync:harness -- --abort`。成功应用后脚本更新 pin。
6. **验证。** 按「合并后验证选择」表执行。
7. **收尾。** 更新同步卡的 `last verified`（替换为本次摘要，不追加流水账）、受影响卡的差异事实、位置索引标记和 `vendor/README.md` 的基线描述。只在用户要求时提交。

其他来源没有通用合并脚本：使用该来源实际仓库的共同基线做三方合并；基线不明时先查清，不猜测，不共用错误基线。任何来源都不整树覆盖，也不机械接受 ours 或 theirs。

### 冲突裁定

| 合并情形 | 处理 | 谁决定 |
| --- | --- | --- |
| 独立改进，或没有行为取舍的接口变化 | 接纳上游，适配受影响的消费者，保持已交付契约 | 在已授权的整合范围内直接完成，说明依据 |
| 上游已提供等价或更完整的能力 | 按现有用户路径、默认行为、数据和权限契约改用上游实现并清理冗余，再验证等价；验证前不宣告差异已消除 | 无行为损失可直接处理；替换理由和实际证据写回负责卡 |
| 同一能力发生行为冲突 | 列出本地与上游行为、保留/融合/替换/暂缓等可行方案、收益损失、迁移影响和建议 | 已有明确产品决定就照办；能力删减、交互或默认值变化、数据或权限取舍交用户决定 |
| 证据不足或必要前置条件缺失 | 保留当前能力，阻塞受影响的整合部分，继续可独立完成的工作 | 未解决项不能默认接纳、标成通过或推进到交付 |

Git 冲突全部解决、编译通过或 fork 标记仍在，都不能证明功能保真。没有文本冲突的语义变化同样按上表处理。已修复的问题不得复发，明确移除或禁用的功能不得随上游恢复。普通冲突在任务状态或提交说明里交代；只有长期架构、兼容性、持久格式或产品取舍才更新[决策记录](../decisions/README.md)。

### 合并后验证选择

在实现和冲突裁定都完成后执行。依据上游增量、最终合并差异和实际受影响的消费者选择对应项；多项命中时合并去重，卡片的 Gates 用来定位必要检查，不自动全跑。这张表选择本地集成验证，正式候选验收范围仍由发布操作说明确定。

| 上游改动触及 | 必要验证 |
| --- | --- |
| 仅文档、导航或翻译 | 改动引用、当前事实和已有配对；不追加安装依赖、产品构建、类型检查或启动 |
| 同步工具、来源校验或差异检查逻辑 | 选择受影响的 `src/shared/harness-sync.test.js`、`src/shared/harness-upstream.test.js` 或 `src/shared/harness-desktop-forks.test.js`；改变 Git 操作时观察相应真实命令行为 |
| 产品源码或共享类型 | 受影响模块和消费者的行为检查，以及其必要构建、类型检查；启动链或跨层集成受影响时执行 `npm run smoke:source` 并重启源码应用 |
| 位置索引登记的包、装配行或标记文件 | 从对应卡的 Gates 选择受影响行为检查；等价迁移时把标记移到新实现，保留原用户行为断言；标记规则变化时验证 forks 检查本身 |
| 插槽、`*.patch.yml` 或 bundle 装配 | 按实际变化选择 vendor 内 `pnpm run verify-client-catalog` 或 `pnpm run verify-cordis-config`，并观察受影响挂载和消费者的真实行为 |
| 依赖、锁文件、原生模块 | 相关依赖准备、正确 profile 构建、锁和闭包检查；依赖声明或许可证清单受影响时执行 vendor 内 `pnpm run verify-third-party-notices` |
| 持久数据、会话格式或配置 schema | 按实际变化选择 vendor 内 `pnpm run verify-persistence-catalog`、`pnpm run verify-session-format-catalog` 或 `pnpm run verify-config-catalog`；验证相应旧数据的真实读取或升级路径 |
| UI、样式或交互 | 相关模块检查，加真实窗口操作观察 |
| Electron、窗口样式或壳集成 | Windows 上运行 `node scripts/run-window-motion-qa.mjs`，交互桌面上再加 `--composed` |
| 分类不明 | 保留完整候选范围 |

依赖准备和官方构建都需要时可用 `npm run setup:harness`，它不是每次同步的固定前置。需要类型检查时，先核对同源码、同 profile 的 host 产物是否已经完成；前置产物满足时使用 vendor 内 `pnpm run typecheck:contracts-ready`，否则使用会先构建 host 的 `pnpm run typecheck`。复用已有产物只消除重复构建，不省略必要类型检查、行为检查或真实操作。

结果绑定合并后的源码。pin 只表示已整合的来源身份，不代表已验证或可以发布。必要本地 QA 未通过或重要冲突未裁定时，不进入最终 CI 和交付。

## 失败、重复与 CI 次数

失败先归类为 product、tool、environment 或 unknown。修好观察器后重新观察原用户路径。环境恢复后的成功不抹去产品首启失败；原因不明就保持 unknown。Bug 修复后保留能发现原故障的复现；能做旧版或受控缺陷对照时证明它会失败，并核对 CI 实际会发现它；做不到就说明限制。

每次追加实验都写清未解问题、改变的条件和结果如何区分不同解释。没有新修改、新失败或具体未覆盖风险时结束验证。复发时优先修覆盖或接线；只有长期系统问题才更新决定或复盘，不用一份新报告当结案。

**CI 次数。** 同一修复目标或发布交付的未通过次数跨提交、版本、候选、分支、工作流和会话累计；一次上游同步算一个交付目标。rerun、取消和超时的计法见[发布操作说明](../handbook/modules/release-process.md)。第四次未通过后停止 CI 和新候选，查清本地为何漏检并提出纠正方案，由用户决定恢复。恢复不清零；之后再有一次未通过，旧的恢复决定就失效。计数不明先查真实 run 历史，未知不等于零。

评价维护效果看实际漏检、复发、未关闭的风险和重复劳动的原因，不用测试数量、文档数量、覆盖率数字或固定耗时作为放行指标。

## 工具入口

```sh
node scripts/run-gates.mjs governance doc-sync                # 维护结构：决定、归档、卡片、rules、链接、配对（去重执行）
node scripts/run-final-gates.mjs --list                       # 列出可选的本地命令
node scripts/run-final-gates.mjs --only desktop-tests         # 只执行明确选中的命令
node scripts/run-final-gates.mjs --check-local-qa <full-sha>  # 最终 CI 前核对本地 QA 记录
node scripts/install-git-integrations.mjs --check             # 只读核对 hooks 和 merge driver
npm run sync:harness -- --dry-run --ref <ref> --sha <sha>     # 上游合并预演
```

- 这些是按需选用的入口，不是每项任务的固定清单。检查成功只说明它实际检查的范围，不代替语义审阅。
- `run-final-gates.mjs` 不接受重复、未知名称或 skip。typecheck 和 test-web 会先构建；pack 和 dist 会强制重建远程组件并校验装配，不作为普通修复的验证入口。
- hooks 的具体行为见 [CONTRIBUTING](../../CONTRIBUTING.md)。hook、插件和记录都不是权限边界，不能保证百分之百拦截。
- 构建和验证使用根目录 `.nvmrc` 指定的 Node 版本。本地 PATH、CI 和已安装应用的运行时是不同环境，分别记录。pnpm 按工作区锁使用，不为统一外观改锁或升级依赖。
- 线上 GitHub 工作流是否已按手动 CI 生效，以实时核实为准；只改本地文件不等于线上生效。
- `docs/superpowers/`、`docs/qa/results/` 和封存决定不参与死链修复；归档保留历史摘要，失败的归档操作不移动或损坏原记录。

取舍理由见[维护决定](../decisions/implemented/process/2026-10-02-maintenance-feedback.md)、[本地 QA 决定](../decisions/implemented/process/2026-10-02-local-qa-first-release.md)和[AI 执行版维护决定](../decisions/implemented/process/2026-10-02-ai-executable-maintenance.md)。外部贡献见 [CONTRIBUTING](../../CONTRIBUTING.md)。

## 常见错误

| 错误做法 | 正确做法 |
| --- | --- |
| 改了一个组件就跑全量 `npm test`，接着派发 CI | 实现完成后从该组件负责卡的 Gates 选择相关检查并验证原故障；范围稳定、本地必要项全通过后再手动派发 CI |
| 测试一直失败，就加 skip 或放宽断言让它变绿 | 先归类失败原因；产品问题修产品，工具问题修工具，然后重新观察原路径 |
| 上游合并没有 Git 冲突，就报告同步完成 | 做影响分析和合并后验证；没有文本冲突的语义变化同样要查 |
| 上游重写了某个组件，直接接受 theirs，桌面定制随之消失 | 查位置索引和负责卡；等价就迁移，不等价就列方案交用户 |
| 环境缺依赖，写“已跳过，不影响” | 标 Blocked，写明缺什么；是否缩小范围由用户决定 |
| 为“以防万一”加 try/catch 兜底和重试 | 指明明确需求、已观察故障或当前契约边界；没有具体依据就不加 |
| 修 bug 前编写“最小复现”测试或搭测试夹具 | 先用已有命令、日志或实际操作诊断并完成修复，再编写必要复现和测试 |
| 上游只改了文档，仍执行 setup:harness、typecheck 和源码启动 | 按实际影响只核对文档；产品构建和运行检查由对应产品风险触发 |
| 只改了文档，却启动应用或打包验证 | 只核对改动的引用、当前事实和配对 |
